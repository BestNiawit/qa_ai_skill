# EP3: เรื่องที่เราเลือกไม่เล่า · skill ที่ตัดทิ้ง, ที่เกือบไม่ได้สร้าง, และตอนที่ให้ AI ทายเวลา (แล้วมันทายไม่เป็น)

> *Recap สั้นๆ ถ้าใครข้าม EP2 มา. ทีม QA เราตั้งต้นด้วยการใช้ ChatGPT แบบมั่วๆ ต่างคนต่าง prompt แล้วเลยลองสร้าง skills เพื่อให้ทุกคนมี context เดียวกัน. EP2 ผมเล่าว่ามันเชื่อมกันยังไงตอนทุกอย่างเข้าที่. EP3 นี่เป็นเรื่องตอนที่มันยังไม่เข้าที่.*

. . .

## *เริ่มด้วยการสารภาพอะไรบางอย่างก่อน*

ตอน EP2 ปล่อยไปแล้ว ผมเขียนปิดท้ายว่า EP3 จะเป็นฉบับ "messier, less polished" คือเรื่องที่ไม่ค่อยอยากเอาขึ้น. พอนั่งเปิด repo มาดูจริงๆ คือมันเยอะกว่าที่คิด.

มี skill ที่ทีมพยายามทำแล้วทิ้ง. มี feature ใน skill บางตัวที่ใส่ไป สามวันก็ตัดออก. มี skill หนึ่งที่ตอนแรกทุกคนเห็นพ้องว่าไม่ต้องทำ พอผ่านไปสี่วันถึงเปลี่ยนใจกัน. แล้วก็มีหนึ่งครั้งที่ผมพยายามให้ AI ทายเวลาที่ทีม QA ใช้ทำงาน (ใน test plan) แล้วมันทายออกมาสวยมาก แต่สวยแบบไม่เกี่ยวอะไรกับความจริงเลย. **ของพวกนี้ไม่ค่อยมีใครเขียนถึง** เพราะมันไม่ใช่ผลลัพธ์ที่ดูดีเวลาเอามาเล่า. แต่จริงๆ คือผมว่ามันเป็นเรื่องที่ช่วยให้คนที่กำลังจะลองทำเข้าใจได้มากกว่าฉบับที่ทุกอย่างผ่านไปด้วยดี.

. . .

## ของที่เคยอยากให้ skill ทำ แต่ตัดออก

อันนี้ไม่ใช่ skill ที่ลบออกจากโฟลเดอร์ตามตัวอักษร. ใน git history เราไม่เคยลบ skill ทั้งตัวเลย. แต่มี **idea กับ feature เยอะมากที่เคย scope ไว้ แล้วตัดทิ้งไป** ในรอบสองสามวันแรก.

เคสที่จำได้ดีสุดเป็น skill ที่อยากให้ generate test data fixtures ตามชนิดของ field. แบบว่าให้ AI ดู schema ของ form แล้วสร้าง JSON dummy ให้ครบทุก data type. ฟังดูเข้าท่ามาก. ลองทำสองวันก็เริ่มเห็นปัญหา. AI สร้าง dummy ที่ดูถูก format แต่ไม่ตรงกับ business rule เฉพาะของ project (เช่น เลขบัญชี 10 หลักของลูกค้านี้ต้องขึ้นต้นด้วย 0 เสมอ). พอ tester เอาไปใช้ แทนที่จะเร็วขึ้น กลับช้ากว่าเดิม เพราะต้องไล่แก้ทุก fixture. สรุปทิ้งครับ.

อีกตัวคือ skill ที่ผมเคยอยากให้ summarize Slack thread เพื่อหา bug pattern ของ sprint. คิดว่าเจ๋งมาก. คิดได้ครึ่งวันก็รู้สึกแปลกๆ ว่ามันออกนอก scope ของ QA tooling ไปไกลเกิน. ทิ้งก่อนเริ่มเขียน SKILL.md ด้วยซ้ำ.

ที่น่าสนใจคือ ทุกตัวที่ทิ้งทิ้งด้วยเหตุผลคล้ายๆ กัน. ผมพยายามจัดกลุ่มดูคร่าวๆ.

> **\[IMAGE: skill-graveyard\]** ตาราง 4 ช่อง · *Test Data Fixture Generator*: AI ไม่รู้ business rule เฉพาะ → output ใช้ไม่ได้จริง · *Slack Thread Summarizer*: ออกนอก scope ของ QA tool · *API Contract Test Generator from Swagger*: overlap กับ test-case-writer · *Regression Risk Predictor*: ต้องการ data ที่ทีมไม่มี.
>
> *Caption: ของที่เคยอยากให้ skill ทำ แต่ตัดทิ้งในสองสัปดาห์แรก*

ของพวกนี้ไม่ได้ทิ้งเพราะ AI ทำไม่ได้. ส่วนใหญ่ AI ก็ทำได้ระดับนึง. มันทิ้งเพราะ **output ไม่มีใครรับช่วงต่อได้จริง** หรือ overlap กับ skill ที่มีอยู่แล้ว หรือมันเก่งในส่วนที่ทีมไม่ได้ขาด. ตอนแรกผมคิดว่าทิ้งเพราะ AI โง่เกินไป. พอย้อนกลับมาดูจริงๆ คือเราเองที่ scope ไม่ขาด.

## `data-type-matrix-generator` ที่เกือบไม่ได้สร้าง

อันนี้กลับด้านกัน. เป็น skill ที่ตอนแรกทีมคุยกันว่าไม่ต้องทำ. เพราะมันดูซ้ำกับ `test-case-writer` ซึ่ง cover boundary value กับ equivalence class อยู่แล้ว.

ลำดับเวลาประมาณนี้.

> **\[IMAGE: dtm-timeline\]** เส้นเวลา 4 วัน · *Day 1 (20 เม.ย.)*: สร้าง 10 skill แรกเสร็จ ทีมตกลงไม่ทำ data-type matrix · *Day 2-3*: ใช้งานจริง พบ TC ขาด edge case ของ THB rounding กับ null handling ซ้ำๆ · *Day 4 (24 เม.ย.)*: pivot, สร้าง data-type-matrix-generator. ระหว่างทาง: ทีมเถียงกัน ~2 ชม. ใน Slack thread.
>
> *Caption: skill ที่เพิ่มทีหลังสุด มาในวันที่สี่หลัง batch แรก*

จุดที่ทำให้เปลี่ยนใจคือมีทีม member คนนึงเอา TC ที่เพิ่ง generate มา review แล้วเจอว่าขาดเคสเล็กๆ น่ารำคาญ. THB rounding ตอนคูณ VAT 7% เลขลงท้าย .005 (round up หรือ down). null กับ empty string ของ field optional. timezone ของ field date ที่ user คนละ region ส่ง payload มา. **ไม่ได้ขาดเพราะ tester เขียน TC ไม่เป็น** มันขาดเพราะ test-case-writer focus ไปที่ scenario กับ flow มันไม่ได้ตั้งใจไล่ทุก data type ของทุก field.

ตอนนั้นถ้าเราดื้อตามแผนเดิมที่ตกลงกันไว้คือ "skill ก็พอแล้วไม่ต้องเพิ่ม" คงไม่มี skill ตัวนี้. สิ่งที่ทำให้เราเปลี่ยนใจคือเรายอมเชื่อ gap ที่เห็นจริงในการใช้งาน มากกว่าตอนเชื่อ tool list ที่วางไว้แต่แรก. ฟังดูเหมือนคำคำนวล แต่ในมุม project management จริงๆ คือมันยากกว่าที่คิด เพราะเปลี่ยน scope หลังเริ่มแล้วต้องไป justify กับทุกคนว่าทำไม.

ผลคือ skill นี้กลายเป็นตัวที่ทีมใช้เป็น defensive fallback ตอน requirement ไม่ชัด. แทนที่จะรอ PM 3 วัน ใช้ skill นี้สร้าง matrix + assumption checklist ส่งไปให้ PM tick yes/no. ลด round trip ไปได้เยอะ.

## ตอนที่ผมพยายามให้ AI ทาย effort

อันนี้คือเรื่องที่ตอนนั้นพอเลิกแล้วก็ไม่ค่อยอยากเล่า เพราะรู้สึกผิดเองที่คิดว่ามันจะ work.

บริบทคือ PM อยากได้ effort estimate ตอน `test-plan-writer` generate เสร็จ. แบบว่า "test plan นี้น่าจะใช้กี่วัน". เป็น request ที่ make sense มาก เพราะ test plan ที่ไม่มีตัวเลขชั่วโมงจริงๆ ก็เอาไป plan sprint ลำบาก.

เลยลอง. เขียน prompt ให้ AI ดู TC sizing (S/M/L/XL) แล้ว estimate hours ออกมา. ผลที่ได้คือสวยมาก. ตัวเลขลงท้ายด้วย .5 บ้าง ลงท้าย integer บ้าง ดูน่าเชื่อถือ. PM happy. ผม happy. นั่งใช้ไปสองสัปดาห์.

แล้วทีมเริ่มสังเกต. estimate ที่ AI ให้ ไม่ตรงกับเวลาจริงสักรอบ. บาง sprint เกินไป 30%. บาง sprint น้อยกว่าจริง 50%. แล้ว pattern ไม่เห็นเลย. มันไม่ใช่แบบว่า "AI underestimate ตลอด" หรือ "overestimate ตลอด" ที่จะ calibrate ได้. มันสุ่มเอา.

ตอนนั้นเริ่มรู้สึกแปลกๆ. เลยลองทำสิ่งที่ควรทำตั้งแต่แรกคือ พล็อต AI estimate vs actual hours ของ 12 sprint ที่เก็บไว้.

> **\[IMAGE: ai-estimate-vs-actual\]** scatter plot สอง axis · X = AI estimate (hours), Y = Actual hours · จุดกระจัดกระจายไม่เป็น line · บางจุด AI ทาย 16 hr ทำจริง 28 hr · บางจุด AI ทาย 24 hr ทำจริง 11 hr · ไม่มี correlation ที่จะ fit straight line ได้.
>
> *Caption: ถ้ามี correlation จุดควรเรียงเข้าหา line. นี่คือไม่มี.*

มันไม่ correlate เลย. ตอนนั้นผมโทษตัวเองอยู่หลายวันว่าเขียน prompt ไม่ดีพอ. ลองปรับ prompt อีก 4-5 versions. ลอง few-shot ด้วย sprint เก่า. ลอง chain-of-thought. ผลก็ยังกระจัดกระจายเหมือนเดิม.

ที่ผมเข้าใจช้าไปคือ effort ของ test execution ขึ้นอยู่กับสิ่งที่ AI ไม่มีทางรู้. ทีม member นี้ถนัด feature นี้หรือเปล่า. environment ตอนนี้เสถียรไหม. มีคนลาในช่วงนี้กี่คน. มี blocker จากทีม dev ค้างอยู่กี่ตัว. **AI ทาย "ทำงานนี้ใช้เวลาเท่าไหร่" ไม่ได้ถ้ามันไม่รู้บริบทของคนทำ** ซึ่งเรานึกว่าเขียน sizing midpoint ไปแล้วน่าจะพอ. ปรากฏว่าไม่พอเลย.

สุดท้ายเลยตัด feature นี้ทิ้ง. ใน `test-plan-writer` ตอนนี้ output คือ effort breakdown ที่คำนวณจากสูตร (TC sizing × buffer policy) ซึ่งเป็น **deterministic** ไม่ใช่ AI ทำนาย. ใน commit history ยังเห็น rule ที่ใส่เพิ่มทีหลังเลยว่า "Schedule ห้ามเดา ต้องคำนวณจาก TC Sizing" ซึ่งอ่านตอนนี้เหมือน rule แห้งๆ แต่จริงๆ มันมาจากสองสัปดาห์ที่ AI ทาย effort แบบสุ่มจนทีมเสียศรัทธา.

## ที่อยู่รอด รู้ขอบเขตของตัวเอง

พอย้อนดู skill ที่ทิ้ง กับ feature ที่ตัด เทียบกับ skill ที่อยู่รอดในระบบ pattern มันเริ่มเห็น.

ของที่อยู่รอดเป็น **skill ที่จัดระเบียบสิ่งที่เรารู้อยู่แล้ว**. test-case-writer จัด requirement ที่ tester อ่านเข้าใจอยู่แล้ว ให้เป็นรูปแบบ TC. bug-report-writer จัด observation ที่ tester เห็นกับตา ให้เป็น Jira ticket ที่ครบ field. test-report-writer จัด data จาก execution ที่มีอยู่จริง ให้เป็น report. ของพวกนี้ AI ทำได้ดี เพราะมัน **map ของที่มีอยู่ ไม่ต้องเดา**.

ของที่ทิ้งหรือถูกตัด feature ออก เป็นของที่เราพยายามให้ AI **เดาในสิ่งที่เราเองยังไม่มีคำตอบ**. dummy data ที่ตรง business rule เฉพาะ. effort estimate ที่ขึ้นอยู่กับบริบทของคน. risk prediction ที่ต้องอาศัย data ที่ทีมไม่มี. AI สร้างคำตอบที่ดูดีให้ได้ครับ ปัญหาคือคำตอบนั้นกับความจริงไม่ตรงกัน แล้วเราไม่มีวิธีรู้จนกว่าจะเอาไปใช้แล้วเจ็บ.

ผมไม่อยากสรุปเป็น principle ที่ฟังดูเท่ๆ. แต่ถ้าจะสรุปแบบใช้งานได้คือ ก่อนสร้าง skill ใหม่ ลองถามตัวเองว่า "AI ตัวนี้ทำให้ของที่มีอยู่จัดระเบียบขึ้น หรือกำลังทายของที่ยังไม่มี". ถ้าคำตอบคืออย่างหลัง ก็ระวังหน่อย. เพราะเรื่องที่เกิดขึ้นกับเรามันก็ไม่ได้ unique. มันแค่เป็นจุดที่หลายๆ ทีมที่ลองทำอะไรแบบนี้น่าจะเจอเหมือนกัน.

## ยังเหลือเรื่องที่ไม่ได้เล่า

ที่เขียนไป 3 เคสนี้เป็นแค่ส่วนหนึ่งของของที่ messy. ยังมีเรื่องที่ skill เคยทำงานพังเพราะ token limit, เรื่องที่ทีมไม่อยากใช้ skill บางตัวเพราะไม่ trust output, เรื่อง onboarding คนใหม่ที่ใช้เวลานานกว่าคิด เพราะ skill มันเยอะเกินจะจำได้หมด.

ของพวกนั้นเอาไว้ EP4 ครับ ถ้ายังมีแรงเขียน. ถ้าไม่มีก็คงจบ series ที่นี่. แต่ EP3 อย่างน้อยก็ได้เล่าของที่อยากเล่าตั้งแต่ตอนปิด EP2 แล้ว.
